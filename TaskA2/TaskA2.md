# Task A2 – Understand Runtime Binding (5 Marks)

## A2.1 – Early and Late Binding (2 Marks)
When invoking a member function through a base-class pointer `Bill* b`, C++ uses two different binding mechanisms depending on whether the function is declared `virtual`:

* **Early (Compile-Time) Binding:** Occurs for **non-virtual** functions (such as `b->show()`). The compiler resolves the exact function address at compile time using only the **static type** of the pointer (`Bill*`), regardless of what derived object `b` actually points to at runtime.
* **Late (Run-Time) Binding:** Occurs for **virtual** functions (such as `b->total()`). Because `b` might point to an `OutPatientBill`, `InPatientBill`, or any other derived object, the compiler emits indirect lookup instructions. At runtime, the program reads the object's hidden virtual pointer (`vptr`) to locate the concrete class's virtual table (`vtable`) and invokes the overridden function matching the object's **dynamic type**.

---

## A2.2 – The Virtual Table (`vtable`) (2 Marks)
Each polymorphic class has one static `vtable` generated by the compiler, and every object instance carries a hidden `vptr` pointing to its class's `vtable`.

### Virtual Table Layouts
```text
+-----------------------------------+

|         Bill vtable               |
+-----------------------------------+

| [0] &Bill::~Bill()                |
| [1] nullptr (pure virtual total)  |
+-----------------------------------+

+-----------------------------------+

|     OutPatientBill vtable         |
+-----------------------------------+

| [0] &OutPatientBill::~OutPatientBill() |
| [1] &OutPatientBill::total()      |
+-----------------------------------+

+-----------------------------------+

|      InPatientBill vtable         |
+-----------------------------------+

| [0] &InPatientBill::~InPatientBill() |
| [1] &InPatientBill::total()       |
+-----------------------------------+
```

### How `b->total()` Reaches the Right Function
Suppose `Bill* b = new InPatientBill(...);`:
1. **Dereference `vptr`:** The runtime follows `b->vptr` to the `InPatientBill vtable`.
2. **Index Lookup:** Since `total()` is at slot `[1]`, it reads the function pointer stored at `vtable[1]`, which is `&InPatientBill::total()`.
3. **Indirect Call:** The CPU jumps to `&InPatientBill::total()` passing `b` as the hidden `this` pointer, executing the `InPatientBill` calculation.

## A2.3 – Virtual Destructors (1 Mark)
When a derived object is deleted through a base-class pointer (`delete b;` where `b` has static type `Bill*`):
* **Without `virtual ~Bill()`:** C++ uses static binding and calls **only `~Bill()`**. The derived class destructor (`~OutPatientBill()` or `~InPatientBill()`) never runs, leaking any memory or resources acquired by the derived class and invoking **undefined behavior** according to the C++ standard.
* **With `virtual ~Bill()`:** Destruction uses dynamic dispatch via slot `[0]` of the `vtable`. It executes `~Derived()` first to clean up derived members, and then automatically chains to `~Bill()` to clean up base members.

### 1. Predicted Output (Written Before Running)

### 2. Actual Output & Explanation
* **Actual Output (with `virtual ~Bill()`):**
  ```text
  500 ~OPBill ~Bill 
  ```
* **How `show()`, a non-virtual function, reached `OPBill::total()`:**
  Although `b->show()` is resolved via early binding to `Bill::show()`, inside `Bill::show()` the call `total()` is implicitly `this->total()`. At runtime, `this` holds the address of the `OPBill` instance whose `vptr` points to `OPBill`'s `vtable`. Because `total()` is `virtual`, `this->total()` dispatches dynamically to `OPBill::total()`, returning `500`.
* **Behavior After Removing `virtual` from `~Bill()`:**
  * **Output changes to:** `500 ~Bill ` (`~OPBill` is skipped completely).
  * **AddressSanitizer (`-fsanitize=address`) report:** ASan immediately aborts with **`ERROR: AddressSanitizer: new-delete-type-mismatch`** because `new OPBill` allocated `sizeof(OPBill)` bytes, whereas non-virtual `delete b` attempts to deallocate only `sizeof(Bill)` bytes (or flags polymorphic deletion without a virtual destructor).

## Alternative Concept and Complexity Analysis

### 1. Alternative Design (`dynamic_cast` Without Virtual `total()`)
If `total()` were non-virtual (with `Bill` still polymorphic via a virtual destructor), the caller would have to inspect the runtime type of each pointer using a chain of `dynamic_cast` checks:

```text
ALGORITHM ComputeTotalWithDynamicCast(bills, count)
    INPUT: bills (array of pointers to Bill), count (integer)
    OUTPUT: grandTotal (real)

    BEGIN
        grandTotal <- 0.0
        FOR i <- 0 TO count - 1 DO
            IF dynamic_cast<OutPatientBill*>(bills[i]) != NULL THEN
                grandTotal <- grandTotal + CALL static_cast<OutPatientBill*>(bills[i]).opTotal()
            ELSE IF dynamic_cast<InPatientBill*>(bills[i]) != NULL THEN
                grandTotal <- grandTotal + CALL static_cast<InPatientBill*>(bills[i]).ipTotal()
            ELSE IF dynamic_cast<DayCareSurgeryBill*>(bills[i]) != NULL THEN
                grandTotal <- grandTotal + CALL static_cast<DayCareSurgeryBill*>(bills[i]).dcTotal()
            ELSE IF dynamic_cast<EmergencyBill*>(bills[i]) != NULL THEN
                grandTotal <- grandTotal + CALL static_cast<EmergencyBill*>(bills[i]).emTotal()
            END IF
        END FOR
        RETURN grandTotal
    END
END ALGORITHM
```

### 2. Time & Space Complexity Comparison

| Metric | Virtual Function (`b->total()`) | `dynamic_cast` Chain (\(k\) bill types) |
| :--- | :--- | :--- |
| **Time per Bill** | **\(O(1)\)** — Constant time (1 pointer dereference + 1 indirect jump). | **\(O(k)\)** — Linear in the number of bill types (up to \(k\) RTTI type-info traversals per bill). |
| **Time for \(n\) Bills** | **\(O(n)\)** | **\(O(n \cdot k)\)** — Degrades as more bill types are added. |
| **Space per Object** | **1 `vptr` (8 bytes on 64-bit systems)** per object + 1 static `vtable` per class. | **1 `vptr` (8 bytes on 64-bit systems)** per object (still required for RTTI `type_info` lookup). |
| **Maintainability** | **High** — Adding a new bill type requires zero changes to caller logic. | **Poor** — Every new bill type forces editing every `if / else if` `dynamic_cast` chain in the program. |
